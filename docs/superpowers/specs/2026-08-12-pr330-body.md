## Summary

Replaces the int-specialized slice-assignment KV write with a single
tensor-indexed indirect scatter, so the write position is **data rather than a
compile-time constant**.

The old `kv_cache_update` took `(is_filling, token_index, cache_position)` as
Python ints threaded into `torch.compile(..., dynamic=False)` blocks. Dynamo
specialized on them, so every distinct `cache_position` produced its own
compiled binary — up to `BLOCK_SIZE` fill binaries plus an expansion binary, per
layer shape. (`torch_spyre` raises Dynamo's `cache_size_limit` to 1024 partly to
survive this.) The new form compiles to **one binary for all positions**
(measured `unique_graphs == 1`).

```python
def kv_cache_update(k, v, key_cache, value_cache, cache_index, source_index=None):
    if source_index is not None:
        k = k.index_select(2, source_index)
        v = v.index_select(2, source_index)
    key_cache.index_copy_(2, cache_index, k)
    value_cache.index_copy_(2, cache_index, v)
    return key_cache, value_cache
```

## Device status: working, gated on torch-spyre#3731

**Resolved.** `index_copy_` was a red herring: the trigger is an **`aten.index` gather whose value operand has higher
host rank than the gather's output** (negative `rank_diff`), reproducible with **no
cache, no scatter, no SDPA and no model**. It hits only the **fill step**, whose
`source_index` gather turns a rank-6 RoPE output into rank-4.

**Genuine Inductor bug** at `propagate_layouts.py:1013-1014`, written assuming
broadcast (`arg rank ≤ output rank`): `rank_diff < 0` is unhandled (the arg's extra
*leading* dims are never added, so the projection comes up short), and the trailing
`-1` sparse-stick marker is silently dropped whenever `rank_diff >= 0`. The same
defect is already worked around at a different call site in
`_inductor/decompositions.py:1101`.

| Fix | Real qwen3 test |
|---|---|
| Inductor-side: repair the projection in `_is_supported_layout` | **PASS**, output `' Paris. The capital of'` |
| hf-adapters-side: gather k/v **before** RoPE | **PASS** (92.7 s) |
| `.clone()` before `index_select` | FAIL — Inductor fuses through it |
| `.contiguous()` after the gather | FAIL |

**How it was actually resolved: neither workaround was needed.** Making the decode
step feed a single token (see below) removes the `source_index` gather entirely, so
the rank-6 operand never exists. The remaining failure was then a *different* bug —
a `seq_len=1` bmm contracting two axes — fixed upstream by
**torch-spyre#3731**, which is required for this PR to pass on device. The
projection bug is filed as **torch-spyre#3732**; nothing here depends on it any more.

Original symptom, for reference:

```
InductorError: Incompatible host_size and dim_order
  propagate_layouts.py:1017 _is_supported_layout
  via _multi_arg_pointwise_layouts, output FixedLayout size=[1, 8, 1, 128]
                                            stride=[1024, 128, 1024, 1]
  failing STL: size=[1, 64, 8, 2, 1, 64] dim_order=[3, 5, 2, 4, 1]
```

Six size entries against five `dim_order` entries. `_is_supported_layout`
projects the output's `dim_order` onto each input via
`[d - rank_diff for d in dim_order if d >= rank_diff]`, which can drop entries and
break the `len(host_size) == len(dim_order)` invariant asserted at
`spyre_tensor_impl.cpp:144`.

Bisected on the real model, all else equal:

| Write | Layout pin | Result |
|---|---|---|
| old slice assignment | off | **passes** |
| `index_copy_` | off | **fails** |
| `index_copy_` | on | **fails** |

So **the layout pin is not the cause**. Ruled out as necessary, all confirmed on
device: the scatter itself, the pinned layout, the SDPA consumer, RoPE specifically,
`seq_len == 1`, `k` as a transposed view, and any multi-layer/graph-size effect.

**Posting for review now** because the plumbing is complete and CPU-verified, and
the signature change is worth team eyes independently of the lowering fix.

## Design decisions, each measured on hardware

**Logical shape unchanged; only the device layout is pinned.** Indirect access
requires the indexed dim at *device* position 0. The `SpyreTensorLayout` decouples
device layout from logical shape, so the cache stays `[B, n_kv, L, head_dim]` —
`index_copy_` writes dim 2 and SDPA reads it directly, **no views**. Logical
permutation cannot substitute; it makes the device position *worse*:

| logical shape | indexed dim | `device_size` | indirect device pos |
|---|---|---|---|
| `[B, n_kv, L, hd]` | 2 | `[8, 576, 2, 1, 64]` | 1 |
| `[L, n_kv, hd]` | 0 | `[8, 2, 576, 64]` | 2 |
| `[L, B, n_kv, hd]` | 0 | `[4, 8, 2, 576, 64]` | 3 |

**In place, not out of place.** `index_copy` (no underscore) allocates a fresh
cache per layer per step *and* returns it with the **default** device layout
instead of the pinned one (measured `[576,8,2,1,64]` in, `[8,576,2,1,64]` out).
Feeding that to the next step's scatter would silently write to wrong rows — see
torch-spyre#3705, where an unpinned indirect scatter writes the right *number* of
elements to the wrong rows with no error. `index_copy_` keeps the pin across
sequential writes and still compiles to one binary. Pinned by
`test_write_is_in_place`.

**`source_index` preserves the old fill semantics exactly.** The previous code
wrote `k[:, :, token_index, :]` — an offset from the **front** of the block, not
its tail. Those coincide only at `token_index == BLOCK_SIZE - 1`, so a tail
assumption would have stored the wrong token's K/V on 63 of every 64 decode steps.
Covered at `tokens_in_block ∈ {0, 1, 17, 63}`.

**Gemma 3 / Gemma 4 used the triple for masks, not the write.** Both computed the
sliding-window band's query coordinates as `block_base = cache_position -
token_index`. Now derived as `int(cache_index[0]) - int(source_index[0])`.
Subtracting `source_index` matters: on a fill step `cache_index[0]` is the written
slot, which differs from the block base by `tokens_in_block`.

## Single-token decode (added after the initial review)

The decode loop now feeds **one token per step** and writes exactly one cache slot,
replacing the FMS block walk that fed `BLOCK_SIZE=64` tokens and stored one. Removed:
the fill/expansion split, `tokens_in_block`, the 64-wide `next_input`, the 64-slot
`result` padding, and the `fill_mask_device` reuse. `build_decode_mask` (a
`[B, 1, 1, max_cache_len]` row) replaces `build_expansion_mask` in the loop, and
`decode_block_walk` becomes a contiguous slice since generated tokens no longer sit in
blocks separated by gaps.

Three consequences worth calling out:

1. It removes the rank-6 `source_index` gather, which is what made the device failure
   look like an `index_copy_` problem.
2. `hf_gemma3` / `hf_gemma4` used the removed int triple for their sliding-window
   band's `block_base` (`cache_position - token_index`), not for the KV write. That is
   now derived as `cache_index[0] - source_index[0]` — subtracting `source_index`
   matters, since on a fill step `cache_index[0]` is the written slot, which differs
   from the block base by `tokens_in_block`.
3. It fixes a real numerics bug: `ministral3`'s batched-`generate` output stopped
   matching stock HF under the block walk and now matches.

`source_index` is retained on `kv_cache_update` for callers that still block-walk
(the three VLM decode loops), and is bit-exact with the old `token_index` slice —
which took its row from the **front** of the block, not the tail, so those coincide
only at `token_index == BLOCK_SIZE - 1`.

## Test-harness and registry changes

`tests/spyre/test_e2e_token_compare_spyre.py` now drives single-token decode too. It
was the last caller of `source_index`, so it hit torch-spyre#3732 and **every model
failed** with `Incompatible host_size and dim_order`. A per-step logits comparison is
only meaningful if it runs the path production runs.

Three models graduated out of `NON_BLOCKING_CAUSAL_MODELS` and now gate CI:

| model | cpu generate | load | smoke | token-compare | |
|---|---|---|---|---|---|
| pythia-410m | XPASS | XPASS | XPASS | XPASS | graduated |
| SmolLM3-3B-Base | XPASS | XPASS | XPASS | XPASS | graduated |
| gemma-3-1b-it | XPASS | XPASS | XPASS | XPASS | graduated |
| Ministral-3-14B | XPASS | XPASS | XPASS | **XFAIL** | kept |
| gemma-4-12b | XFAIL | XFAIL | XFAIL | XFAIL | kept |

That table is why graduation was checked in all four harnesses rather than the one
that first showed an XPASS: the marker is per-model and shared, and `ministral3`
xpasses three of four while still failing Spyre token-compare numerics. Unmarking it
on the CPU signal alone would have turned a non-blocking xfail into a hard CI
failure. `gemma-4-12b` fails everywhere on a pre-existing transformers
per-layer-attribute config error that reproduces on an unmodified tree.

## Not changed

Mask builders (`build_prefill_mask`, `build_expansion_mask`,
`add_causal_sliding_window_band`) and cache-coordinate semantics (column `c` holds
absolute position `c - prompt_offset`). Keeping the mask contract fixed is what
bounds this change.

## Out of scope

- Paged KV / block tables / continuous batching.
- Narrowing the SDPA read window to live slots only.

## Review asks

1. **Is `source_index` the right seam**, or would you rather the fill step feed a
   single token and drop the parameter (pulling the decode-width change forward)?
2. **`assert_kv_cache_layout`** is the only automated guard against a lost pin —
   CPU cannot detect one. Is it wired in the right place, and should it be
   assert-always or debug-only?
3. **The `int(cache_index[0])` reads** in the Gemma 3/4 mask paths sync a scalar
   from the device. I've accepted this for now and documented why inline: it runs
   once per step (not per layer), in eager code outside the compiled block, and
   `add_causal_sliding_window_band` already round-trips the whole mask through CPU
   by necessity — so the scalar read is noise beside it. Gemma 3/4 are the *only*
   adapters that read a scalar out of `cache_index`. The real fix is hoisting the
   per-layer-type mask construction out of the forward pass entirely (the decode
   loop knows every step's `block_base` in advance), which this PR deliberately
   leaves alone since its boundary is "mask builders unchanged". Flagging in case
   you'd rather see it done here.
